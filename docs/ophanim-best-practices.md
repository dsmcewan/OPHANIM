## Instructing a model

Writing instructions and system prompts, roles, examples, controlling the form of the answer.

**Where the labs agree**

- OpenAI, xAI and Anthropic each say a task prompt should state the task and its constraints directly and say what a finished result looks like. (anthropic, openai, xai)
- OpenAI, Google and Anthropic each say to separate the parts of a prompt with Markdown headings or XML tags so the model can tell instructions from supplied content. (anthropic, google, openai)
- OpenAI, xAI and Anthropic each say conflicting or ambiguous instructions make results worse or get resolved arbitrarily, so contradictions should be removed. (anthropic, openai, xai)
- OpenAI, xAI and Anthropic each say short, specific standing instructions are followed more reliably than long or vague ones. (anthropic, openai, xai)
- OpenAI, Google and Anthropic each say not to ask a reasoning model to think step by step or write out its reasoning in the answer. (anthropic, google, openai)
- Google, Anthropic and xAI each point to a structured output feature, not prompt wording or a prefilled model turn, as the way to hold a schema-bound answer to its form. (anthropic, google, xai)
- OpenAI, Google and Anthropic each say instructions written to compensate for an older model should be revisited when the model changes, because they can now hinder the newer one. (anthropic, google, openai)
- OpenAI, xAI and Anthropic each say emphatic or absolute wording should be used sparingly, because overuse dilutes it or makes the model over-apply the rule. (anthropic, openai, xai)
- xAI, Anthropic and Google each say to tell the model what to do when it lacks the information, including saying it does not know, instead of leaving it to invent. (anthropic, google, xai)

**Where they differ**

- Google says to always include few-shot examples and that prompts without them are likely less effective. OpenAI says to try reasoning models with no examples first, while Anthropic recommends three to five examples and, with caching, twenty or more. (anthropic, google, openai)
- An OpenAI cookbook says to give clear, concrete length limits in coding agents. Google says its model does not follow token-length or word-count targets, and Anthropic says hard limits are followed literally and that one such system prompt line reduced coding quality. (anthropic, google, openai)
- OpenAI keeps absolute words such as ALWAYS and NEVER for true invariants like safety rules. Anthropic says to drop shouted emphasis for current models and move a rule the model keeps missing into a hook, though one of its engineering posts still uses strongly worded instructions to protect tests. (anthropic, openai)
- OpenAI sets how prescriptive a prompt should be by model class: high-level goals for reasoning models, longer and more explicit prompts with a full execution order for smaller models. Anthropic sets it by the task, with exact instructions for fragile operations and general direction for open ones, and xAI adds explicit phases only when an agent skips steps. (anthropic, openai, xai)
- OpenAI puts rules and business logic in developer messages. Google accepts either the system instruction or the very start of the user prompt for constraints, role and format, while Anthropic says instructions in a user message carry slightly less weight than the same text in the system prompt. (anthropic, google, openai)
- On what the prompt should say about a schema-bound answer: xAI says the prompt need not restate the fields and orders the schema so evidence fields come first, Google says not to state a field order in the prompt and to make all fields required, and an OpenAI cookbook says to repeat the output instruction near the top and near the bottom. (google, openai, xai)
- The default output differs by lab. OpenAI says its model tends to lists, tables and Markdown so prose must be requested, while Google says its models answer directly and tersely so a longer or more detailed answer must be requested. (google, openai)

## What a model is given to read

What goes into the context window and what stays out, long context, compaction, memory across sessions, retrieval.

**Where the labs agree**

- All four labs say to send the model's earlier output items, reasoning or thinking included, back exactly as received and to keep the conversation history append-only. (anthropic, google, openai, xai)
- OpenAI, xAI and Anthropic say compaction must run before the conversation outgrows the model's window, because the window sent for compaction must itself still fit. (anthropic, openai, xai)
- OpenAI, xAI and Anthropic say to pass the compaction output into later requests exactly as returned, without pruning it. (anthropic, openai, xai)
- OpenAI, Google and Anthropic say that long or growing context lowers quality, so context is managed to keep the model focused and not only to fit the window. (anthropic, google, openai)
- OpenAI, Google and Anthropic say to leave out what the model does not need and send only the context that bears on the task. (anthropic, google, openai)
- OpenAI, xAI and Anthropic say to cut tool output down before it enters context, and the Codex and Claude Code products both move oversized output to a file and give the model its path. (anthropic, openai, xai)
- OpenAI, Google and Anthropic say to keep always-loaded instructions small and to load procedures and reference material only when the task calls for them. (anthropic, google, openai)
- OpenAI, xAI and Anthropic say stored memory is not authoritative: it can be stale or wrong, so mandatory rules and changing facts must come from a checked source. (anthropic, openai, xai)
- OpenAI, xAI and Anthropic each say a compaction item does not carry everything, so some things must be sent again after it: tools added mid-conversation (OpenAI), the system prompt (xAI), mid-conversation instructions and attachments (Anthropic). (anthropic, openai, xai)

**Where they differ**

- Google says its large window invites the more direct approach of providing all relevant information up front. OpenAI says putting everything into a long context costs accuracy and must be evaluated at different context sizes, and Anthropic says more context is not automatically better because accuracy and recall degrade as tokens grow. (anthropic, google, openai)
- OpenAI's compaction item is opaque and not meant to be read by people. Anthropic's compaction block holds the summary as readable text with a signature, and Anthropic lets the caller replace the summarisation prompt. (anthropic, openai)
- xAI advises a smaller, faster model for the compaction call when compacting often. Anthropic's server-side compaction always summarises with the request's own model and offers no cheaper one. (anthropic, xai)
- Compaction triggers differ: Google's managed agent compacts at about 135k tokens, Grok Build at 85% of the window, Claude Code at about 967K tokens on 1M-window models, and Anthropic's API threshold cannot be set below 50,000 tokens. On timing, OpenAI says to compact after major milestones and not every turn, xAI suggests every N turns or a chosen threshold, and Anthropic says to try later compaction points. (anthropic, google, openai, xai)
- Placement around a summary differs: OpenAI says a home-grown compacted item goes at the end of the context and not before recent turns, Anthropic says to put the block in front of the turns that were kept, and xAI says the item must come first because the API drops everything before it, instructions included. (anthropic, openai, xai)
- What server-side state carries differs: on OpenAI a developer message in the first input stays in the chained history, while Google's Interactions API says request parameters must be re-specified in every new interaction. (google, openai)
- For a long session, OpenAI's Codex guidance is to stay in the same chat and compact while the objective is unchanged, forking only when it diverges. Anthropic says to consider a brand new context window that rediscovers state from files instead of compacting, which depends on the handoff artifact holding enough state. (anthropic, openai)

## How hard a model thinks

The reasoning or thinking control: when to raise or lower it, defaults, and what it costs.

**Where the labs agree**

- All four labs describe effort as a trade: a higher level buys deeper reasoning and possibly better results on complex work, and costs latency and tokens. (anthropic, google, openai, xai)
- All four labs say to set the effort level explicitly instead of taking a default, because the default differs between models and changes when a model is swapped. (anthropic, google, openai, xai)
- All four labs say to choose the level by running your own evaluations at more than one level and keeping the lowest one that holds quality, not by intuition. (anthropic, google, openai, xai)
- All four labs reserve the top levels (xhigh, max) for the hardest problems, and OpenAI, Google and Anthropic add that they should not be a default and can overthink simple tasks. (anthropic, google, openai, xai)
- All four labs bill reasoning tokens, and OpenAI, Google and Anthropic state that this holds even when the reasoning text is not returned. (anthropic, google, openai, xai)
- OpenAI, Google and Anthropic say to reduce thinking by lowering the effort level, not by a small output-token cap, because a cap reached during reasoning returns truncated or empty output that is still billed. (anthropic, google, openai)
- All four labs point low effort at simple, well-scoped or latency-sensitive steps such as picking the next tool, classification or a single search. (anthropic, google, openai, xai)
- All four labs report that too little effort on multi-step agent work makes the model skip steps or checks or stop early, and that more effort keeps it on the task through its checks. (anthropic, google, openai, xai)
- OpenAI, Google and Anthropic say that a harness managing its own history must send back the model's reasoning items or thought blocks unchanged during tool use. (anthropic, google, openai)

**Where they differ**

- The default level is not the same anywhere: OpenAI treats medium as the default and starting point; xAI's current models default to high while grok-4.3 defaults to low; Google thinks dynamically by default and Gemini 4 Hydrogen defaults to high; Anthropic's API defaults most models to high and Opus 5.5 and Haiku 5.5 to medium. Anthropic's own product differs from its API: Claude Code runs Fable 5.2 at medium where the API default is high. (anthropic, google, openai, xai)
- Whether reasoning can be switched off differs. OpenAI has a none level and suggests it for execution-heavy steps; xAI says reasoning cannot be disabled on current models though grok-4.3 accepts none; Google says minimal does not guarantee thinking is off and Hydrogen rejects minimal; Anthropic's newest models cannot turn thinking off, the lowest setting is between_tools, and Anthropic advises low effort with thinking on over disabling it. (anthropic, google, openai, xai)
- What the output-token cap covers differs. On OpenAI, Google and Anthropic the cap counts reasoning plus visible output; on xAI max_output_tokens caps only the visible answer and reasoning tokens do not count toward it. (anthropic, google, openai, xai)
- The labs order the levers differently. OpenAI calls effort a tuning knob, not the main way to recover quality, and says to check the prompt for a missing success criterion or verification loop before raising it; Anthropic calls effort the primary control and says to raise effort for shallow reasoning instead of prompting around it; Google says to tune the thinking level before changing model. (anthropic, google, openai)
- Prompt cues to think harder are treated differently. Google says a request such as "Think very hard" can improve hard problems; Anthropic's platform guide says "think thoroughly" often works better than a prescribed plan, while Claude Code treats such phrases as ordinary text and an instruction not to deliberate did not stop thinking at medium and above; an OpenAI cookbook says asking a reasoning model to plan more before each tool call may hurt performance. (anthropic, google, openai)
- Changing effort inside a conversation differs. OpenAI supports it through configuration_update items while keeping the request-level value fixed for the cache; Anthropic says to pick one top-level effort per conversation and keep it, and returns a 400 for a per-message change under between_tools; xAI says to set the level on every request. (anthropic, openai, xai)
- An unsupported or odd value is handled differently. xAI silently treats xhigh as high on models that lack it and, on its multi-agent model, uses the effort parameter for the number of agents; Google's Hydrogen rejects minimal with an error; Anthropic returns a 400 for between_tools at xhigh or max, while Claude Code lowers an unsupported level to the highest supported one. (anthropic, google, xai)

## Tools and structured output

Designing tools and functions, their descriptions and schemas, structured output, handling results, MCP.

**Where the labs agree**

- Give the model only the tools the task needs and keep the active set small, because every definition takes context and selection gets worse as candidates grow; when the library is large, defer definitions behind tool search or retrieval. (anthropic, google, openai, xai)
- The model picks and fills a tool from its description, so each description must say clearly what the tool does and when to call it. (anthropic, google, openai, xai)
- Type parameters specifically, use an enum where the valid values are a fixed set, and prefer flat schemas to deeply nested ones. (anthropic, google, openai)
- Return a failed tool call to the model as an error result with a message it can act on, so it can correct the call or retry. (anthropic, google, openai, xai)
- A schema fixes the shape of an output, not its correctness: the application must still validate values and handle refusals, incomplete responses and schema keywords the lab does not enforce. (anthropic, google, openai, xai)
- Function calling is for intermediate actions against your own systems, and structured output is for the shape of the model's final response. (anthropic, google, openai)
- One response can carry several tool calls among other items, so the handler must read items by type rather than position, run every call, and return a result for each call matched by its id. (anthropic, google, openai, xai)
- Tool results should be compact and structured, carrying only the fields the next step needs, with large payloads cut, paginated or passed by reference. (anthropic, google, openai)
- A tool's self-declared annotations, such as a read-only hint, are hints for clients and must not be relied on for enforcement or security. (anthropic, xai)

**Where they differ**

- OpenAI recommends always enabling strict mode, and Responses attempts it by default with a silent fall-back to non-strict; on xAI strict is implicitly always true; Anthropic caps strict tools at 20 per request and says to mark only critical tools strict. Anthropic's newest models also reject a forced tool choice, while Google offers a validated calling mode to reduce malformed calls. (anthropic, google, openai, xai)
- Labs treat schema keywords they cannot enforce differently: Google strips and ignores them without an error, xAI accepts them but does not structurally enforce them, and Anthropic sends the model a simplified schema and leaves the constraints to an SDK helper, with nothing checking them when a raw schema is passed. (anthropic, google, xai)
- Anthropic asks for very detailed tool descriptions of at least three to four sentences, while OpenAI's cookbook asks for one or two crisp sentences and its guide suggests shortening descriptions when token limits are hit. (anthropic, openai)
- Anthropic says to group related actions into one tool with an action parameter, Google says to split monolithic functions into smaller focused tools, and OpenAI says to merge only functions that are always called in sequence. (anthropic, google, openai)
- OpenAI and Anthropic each say to use the edit tool their own model was trained on, but the formats differ: OpenAI's apply_patch diff format against Anthropic's exact string replacement. xAI's worked example writes whole files and notes passage replacement only for large codebases. ## Running a model as an agent

The agent loop and harness, long-running work, planning, checkpoints and handoffs, subagents and delegation.

**Where the labs agree**

- OpenAI and Anthropic both say to start with one agent or the simplest design and to add agents or a second model only when a specific need or a measurement justifies it. (anthropic, openai)
- OpenAI, Anthropic and xAI all say more agents use more tokens, and OpenAI and Anthropic say delegation does not pay for work that is one dependent chain. (anthropic, openai, xai)
- OpenAI, xAI and Anthropic say parallel agents must not edit the same files and should each work in their own git worktree or checkout. (anthropic, openai, xai)
- OpenAI, xAI and Anthropic describe a subagent as a separate context that does not receive the parent's whole conversation and that hands a summary or final result back. (anthropic, openai, xai)
- All four labs recommend a planning step before editing or executing on complex or ambiguous work. (anthropic, google, openai, xai)
- xAI, Google, Anthropic and OpenAI's worked examples all bound the agent loop with an explicit limit on turns, attempts, tokens or spend. (anthropic, google, openai, xai)
- OpenAI, xAI, Google and Anthropic say to save state as the run goes so an interrupted run resumes where it stopped instead of repeating finished calls. (anthropic, google, openai, xai)
- OpenAI and Anthropic say a quiet or ended session is not proof of success: check the explicit outcome and whether anything the agent started is still running. (anthropic, openai)
- OpenAI, Google and Anthropic keep the harness or conversation state separate from the sandbox that executes the work, so each can be persisted, reused or replaced on its own. (anthropic, google, openai)

**Where they differ**

- Google's managed agents do not support subagent delegation, Anthropic's managed agents allow one level, and Claude Code allows three layers by default. Default concurrency differs too: OpenAI's managed harness runs 6 subagents and its Responses multi-agent setting 3, while Claude Code allows 20. (anthropic, google, openai)
- Google offers a total-token limit that stops the run as incomplete on a best-effort basis. Anthropic's task budget is a soft hint the model may exceed and its Agent SDK turn and spend limits have no default, while xAI applies a server-side default turn cap whose counter resets at each client-side tool call. (anthropic, google, xai)
- At a turn limit xAI's agent stops calling tools and writes a final answer from what it has gathered, while Anthropic's Agent SDK ends the run with an error and no final response unless a turn was left for it. Google returns status incomplete with the work and context preserved for a follow-up. (anthropic, google, xai)
- OpenAI says its model may delegate less often than wanted and tells developers to specify when to use subagents. Anthropic says its model tends to spawn subagents where a direct approach would do and tells developers to review standing instructions to delegate. (anthropic, openai)
- OpenAI prescribes a prompted progress-update cadence for coding agents (every 1 to 3 steps, at least every 6 steps or 10 tool calls). ## Checking the work

Evals, testing an agent's output, review and grading, self-checking, measuring quality.

**Where the labs agree**

- A completed turn or an agent's confident summary does not establish that the work succeeded; inspect the output or rerun the check. (anthropic, google, openai, xai)
- Use code checks where they are reliable and a model judge only for what code cannot decide. (anthropic, google, openai, xai)
- Give a model judge a specific rubric with examples of score levels and have it reason before it gives its score. (anthropic, openai, xai)
- Measure a model judge's agreement with human labels on a sample before relying on it at scale. (anthropic, openai, xai)
- Write down what success means in measurable terms before the work or the test is run. (anthropic, google, openai, xai)
- Because model output varies between runs, run each case several times instead of trusting a single run. (anthropic, google, openai, xai)
- Build test sets from data representative of real use and add edge cases. (anthropic, google, openai, xai)
- Have work checked by a reviewer that is separate from the instance that produced it. (anthropic, openai, xai)
- Run the eval suite again when the prompt or the model changes. (anthropic, google, openai)

**Where they differ**

- OpenAI recommends grading the trace: whether the agent called the right tool with the right arguments and what actually happened in the run. Anthropic's engineering posts call checks on tool-call sequences brittle and say to grade what the agent produced, although Claude Code's plugin evals pair one grader on the result with one on the steps. (anthropic, openai)
- OpenAI says to ask the model to verify that it completed the work, and Google's prompt template includes a validate step. Anthropic makes this per model: verification and double-check instructions cause over-verification on Claude Opus 5 and should be removed, while the same kind of text improved Claude Haiku 5.5. (anthropic, google, openai)
- OpenAI's Codex review flags only P0 and P1 issues and OpenAI says review models must be tuned for those. Anthropic says a reviewer told to report only high-severity issues may report less, so ask it to report everything and filter in a separate pass. (anthropic, openai)
- An OpenAI blog example starts its release review from "safe to release" and blocks only on concrete evidence in the diff. Anthropic tunes a standalone evaluator to be sceptical and instructs its reviewer only to find problems. (anthropic, openai)
- The labs aggregate judgments differently: xAI's Grok Build marks a goal complete when most of a panel of reviewer subagents agree and Claude Code's plugin evals take two of three judge votes, while Anthropic's research system found a single judge call most consistent. Google's guidance instead asks narrow questions and uses the answer's confidence in code to act or escalate. (anthropic, google, xai)
- OpenAI says to use human expert labellers and Google says you will likely need to build test sets with human raters. Anthropic says more questions with automated grading are better than fewer hand-graded ones. (anthropic, google, openai)
- Google says to focus on worst-case performance across the evaluation set rather than the average. xAI says to report the mean and spread and use pass@k where any one correct attempt counts, and Anthropic says the choice between pass@k and pass^k depends on whether one success or consistency matters. (anthropic, google, xai)

## Containing a model

Sandboxing, permissions and approvals, prompt injection, secrets, untrusted content, guardrails.

**Where the labs agree**

- OpenAI, Anthropic and xAI say prompt instructions state intent but enforce nothing, so access limits belong in permissions, the harness or the tool server. (anthropic, openai, xai)
- OpenAI, xAI and Anthropic treat permissions or approvals (which calls may run, and when to ask) and the sandbox (what a call can reach) as two separate controls that are used together. (anthropic, openai, xai)
- OpenAI, Google and Anthropic say code the agent runs can read and use any credential in its environment, so environment variables in the sandbox are not a place for secrets. (anthropic, google, openai)
- OpenAI, Google and Anthropic keep the real secret outside the sandbox, give the code inside a placeholder and have a proxy add the secret only to requests for listed hosts, and xAI's example runs model-written commands without the environment that holds the API key. (anthropic, google, openai, xai)
- OpenAI, Google and Anthropic restrict a sandbox's outbound network to an allowlist of hosts, and OpenAI and Anthropic both require exact host names without wildcards and treat every allowed host as a route by which data can leave. (anthropic, google, openai)
- All four labs say content an agent reads from websites, repositories, files or tool results is untrusted data that cannot grant permission or override the user's instructions. (anthropic, google, openai, xai)
- All four labs say to stop for a person's confirmation before a tool call that is high-risk, has significant consequences or cannot be undone. (anthropic, google, openai, xai)
- OpenAI, xAI, Anthropic and Google say no single defence is enough: model-based review, input sanitising and classifiers add to isolation, least privilege and explicit approval, and do not replace them. (anthropic, google, openai, xai)
- All four labs warn against one agent step that holds both untrusted content and private data or side-effecting tools, and OpenAI, xAI and Anthropic split reading from acting into separate requests, steps or agents. (anthropic, google, openai, xai)

**Where they differ**

- Product defaults for containment differ: Codex and OpenAI's hosted containers start with no outbound network, Google's agent sandbox is isolated at the OS level but has unrestricted outbound network until an allowlist is set, and xAI's Grok Build sandbox is off by default. Claude Code's sandbox covers shell commands only and by default lets them read most of the machine, including credential files. (anthropic, google, openai, xai)
- OpenAI tells harness builders to fail closed when review times out or is unavailable, and Claude Code denies an action when its classifier returns no verdict. Google's and xAI's hooks treat a crash, timeout or malformed output as allow, and a crashing guard callback in Anthropic's Agent SDK also lets the call go on to the normal permission flow. (anthropic, google, openai, xai)
- What happens when nothing is configured differs: OpenAI's managed agent sessions default to no review and do not send actions to the application for approval (its MCP connector does ask by default), while Anthropic's MCP toolsets default to always_ask and Claude Code headless and SDK runs start in Manual mode. xAI offers dontAsk for headless runs, which silently denies anything without an allow rule. (anthropic, openai, xai)
- OpenAI's automatic reviewer uses the conversation context to judge an action. Anthropic's classifier is given only the user messages and the agent's tool calls, with the agent's own text and tool results stripped so that neither the agent nor hostile content can argue with it. (anthropic, openai)
- The labs place untrusted text differently in a request: OpenAI says pass it through user messages and never developer messages, while Anthropic says keep it inside tool_result blocks and never in system prompts or plain user text blocks. (anthropic, openai)
- Codex interrupts the turn after 3 consecutive reviewer denials or 10 in the last 50 reviews. Claude Code pauses automatic approval after 3 consecutive or 20 total blocks, and in non-interactive runs the blocked action does not run but the run continues. (anthropic, openai)
- Google calls a blocklist of prohibited websites a good starting point, with an allowlist more secure; Anthropic says not to rely on blocked domains for security at all. (anthropic, google)

## Operating across labs

Choosing and migrating models, deprecations, caching, batch, rate limits, retries and errors, cost.

**Where the labs agree**

- All four labs say to put stable content (instructions, tool definitions, reference material) at the start of the request and changing content at the end so the prefix can be cached; OpenAI, xAI and Anthropic add that editing earlier turns or tool definitions invalidates the cache from that point. (anthropic, google, openai, xai)
- All four labs say to retry 429 and 5xx responses with exponential backoff; OpenAI, Google and Anthropic add that billing, quota and spend-cap errors will not succeed on retry. (anthropic, google, openai, xai)
- The official SDKs of OpenAI, Google and Anthropic retry transient errors on their own; OpenAI says to disable or count those retries when the application also retries, and Anthropic's SDK exposes max_retries to configure or disable them. (anthropic, google, openai)
- All four labs offer a batch API for work that needs no immediate answer, kept apart from the synchronous rate limits, with completion expected within about 24 hours. (anthropic, google, openai, xai)
- OpenAI, Anthropic and Google say a model change needs its own check: run the replacement on your own requests before switching, and re-measure cost rather than assume it carries over. (anthropic, google, openai)
- OpenAI and Anthropic pair a stronger model for planning and hard decisions with a cheaper one for execution and narrow high-volume work, and Google likewise says to match the model to the task. (anthropic, google, openai)
- OpenAI, xAI and Google say a low output cap cuts the response short, and OpenAI and xAI say to treat an incomplete status as a truncated answer; Anthropic warns that a cap tuned for an older model can cut off equivalent output. (anthropic, google, openai, xai)
- OpenAI, Google and Anthropic say to branch error handling on a machine-readable code or typed error class, not on message text. (anthropic, google, openai)
- OpenAI, Anthropic and xAI say a burst or a sharp rise in traffic can be refused even when usage is under the per-minute limits. (anthropic, openai, xai)

**Where they differ**

- Anthropic uses explicit cache_control breakpoints (four slots) with a 5-minute default lifetime and a 1-hour option at extra cost, while OpenAI's default lifetime is 30 minutes with a 12-hour option and cache writes cost 1.25 times uncached input. Google's Gemini 4 models have only implicit caching with no saving guarantee, and xAI asks for a per-conversation prompt_cache_key to route turns to the server that holds the cache. (anthropic, google, openai, xai)
- OpenAI says cached input tokens still count toward tokens-per-minute limits and Google says token limits include cached tokens, while Anthropic counts only uncached input toward its input-token rate limit. (anthropic, google, openai)
- OpenAI computes the rate limit from max_tokens and says to set it close to the expected response size; Anthropic says max_tokens does not factor into its output-token rate limit, so a higher value has no rate-limit cost. Google tells Gemini 4 users to remove low caps and lower the thinking level to save tokens instead. (anthropic, google, openai)
- OpenAI, Anthropic and Google say to omit temperature and top_p on their newest models; xAI says to set temperature to 0.7 and top_p to 0.95 and not move far from those values. (anthropic, google, openai, xai)
- OpenAI and Google say to cap retry attempts, and OpenAI also the total time spent; xAI says to rerun a request that still fails until it gets a response. Defaults differ too: Anthropic's SDK retries twice, Google's Python SDK up to four times, Codex four times for provider HTTP requests, and Claude Code ten. (anthropic, google, openai, xai)
- OpenAI gives at least 6 months' notice for generally available models (as little as 2 weeks for previews) and exposes a shutdown_date field, Anthropic gives at least 60 days, and Google lists only earliest possible dates. Google routes some retired ids to another model billed at that model's rates, and xAI advises choosing the replacement explicitly before the date to avoid cost increases. (anthropic, google, openai, xai)
- An expired batch behaves differently by lab: OpenAI makes responses to completed requests available and cancels the rest, Anthropic gives access to results after 24 hours, and a Google job that expires after 48 hours has no results to retrieve. xAI calls its completion time best effort and not guaranteed. (anthropic, google, openai, xai)
