# The public record

GitHub is OPHANIM's public-facing operational record. It is a readable, navigable **projection** of the
internal ledgers, which stay authoritative. It is not an orchestration system: nothing in OPHANIM or
Pantheon reads GitHub to decide anything. An outside developer can follow a capability from investigation,
through assigned work and competing approaches, to independent verification and acceptance, and can check
every step against the ledger from a clone of the repository.

## What is projected, from where

| On GitHub | From | Generated by |
|---|---|---|
| One issue per status item | the status ledger, `status/ledger` (`packages/ledger/status.mjs`) | `node ophanim/public/github.mjs apply` (workflow `public-record.yml`) |
| Labels `state:*`, `waiting:*`, `role:*`, `decision-authority` | the same entries | the same |
| A "Provenance" section in a pull request body | a system or review-cycle ledger (`pantheon/src/ledger/{cycle-kinds,review-cycle,lineage-kinds}.mjs`) | `node ophanim/public/github.mjs pr-provenance --ledger DIR` |
| `docs/cycles/<scope>-<n>.md`, `docs/cycles/index.md` | the review-cycle ledger (`npm run review-cycle`) | `node ophanim/public/github.mjs cycles` |
| The workflow run summary | the run's own test logs and `node packages/ledger/status.mjs verify` | `ophanim/public/ci-summary.mjs` in `qualification.yml` |

### Issues

Each issue body carries, in this order: what needs doing (the item's title and id), why it matters (the
recorded basis), its state (what it waits on, when it was last checked, its owner role if the ledger records
one), its dependencies and dependents as links to their issues, its full status history (every change, with
the date it was checked and the ledger entry hash), the agent provenance notice, and a **Verify this
record** section naming the ledger's genesis anchor and the item's latest entry hash, with the commands to
check them:

```sh
node packages/ledger/status.mjs verify
node ophanim/public/github.mjs verify-item <item> <entry>
```

When the item's latest status was recorded from a Pantheon board run's proposal (`docs/operating-workflow.md`)
it carries an `evidence` object, and the body gains an **Evidence** section before the history: the run
ledger's anchor and head, the run.json digest, the gate verdict entry, the review cycle with its close and
outcome, a table of the reviewers (vendor, requested model, served model, lab), the commit, the tests and
the ticket, and whether the cited ledgers were re-checked when it was applied. Only then does the
provenance notice claim independence, from the cited cycle's distinct labs; the reviewers are still model
seats, shown as text and never as GitHub identities. History rows recorded with evidence are marked so.

Resolved items are closed as completed; every other item is open. The body is deterministic in the ledger
(it carries no generation time and no ledger head), so an unchanged item is never rewritten.

### Labels

- `state:resolved`, `state:in-progress`, `state:ready`, `state:on-hold`: the item's state.
- `waiting:governance|credential|evidence|fact|decision`: what a hold waits on, outside the work.
- `role:impl@build`, `role:check@review`, `role:lead@orch`, `role:scout@opt`, `role:arbiter@judge`: the
  chair (model seat) that owns the item, from the optional `owner_role` field of a status entry.
- `decision-authority`: an item only the human owner decides. Set from `owner_role: decision-authority`, or
  from a hold whose `waiting_on` is `decision`.

`owner_role` is optional and was added after the first entries were recorded; an item without it shows
"Owner role: not recorded on the ledger" rather than a guess.

## Agent roles and GitHub identities

This is the rule that matters most.

1. **One account.** All GitHub activity on the public record (issues, labels, comments, provenance
   sections) is posted by one account: the workflow's `GITHUB_TOKEN` (github-actions) or the repository
   owner. There is no GitHub account per model seat.
2. **Seats are not developers.** The roles named on the record are model seats operated under that
   account. They are not independent developers and are never presented as such.
3. **No GitHub identity for a seat.** GitHub assignees, requested reviewers and pull request approvals are
   never used for agent seats. A seat appears only as a `role:` label and as text with its ledger evidence.
   A review by a seat is a ledger entry signed by that seat's own key, never a GitHub review.
4. **Assignees are people.** The only assignee the publisher ever sets is a real person, on a
   `decision-authority` item, and only when one GitHub login is configured (`OPHANIM_OWNER_LOGIN`, a
   repository variable). By default nobody is assigned. The publisher only adds that assignee; it never
   removes an assignee or a label a person added.
5. **Independence is claimed only where the ledger shows it,** and each claim carries its evidence:
   - reviews on **distinct labs**, none of them the lab that authored the change (re-derived from each
     review's vendor and served model);
   - the **cold-review check passed**: the ledger verified in full, and a review whose lab, seat or
     response is in the lineage of what it reviews does not re-derive;
   - the **served model reported** by the provider, beside the requested one;
   - for every seat: seat key id, vendor, requested and served model, lab, ledger entry hash.

   Where the ledger shows none of this (a status item, for example), the record says that no
   independence is claimed.
6. **The limits are stated with the claim.** Distinct labs are distinct model vendors, not distinct people
   or organisations, and do not establish independent training data. The served model is what the
   provider reported; the ledger records it and cannot observe it. Re-derivation checks signatures,
   citations and the cold-review rule; it does not run tests or reproductions, and fail-before /
   pass-after exit codes are recorded data, checked for consistency only. A finding without a reproduction
   can be deferred, and such a cycle closes `unverified`, never `verified`.

Every generated body carries an **Agent provenance** notice saying this.

## The publisher

`ophanim/public/github.mjs` (projection in `record.mjs`, pull request and cycle projections in
`provenance.mjs`):

- `plan` (the default) is a dry run: it reads the status ledger, which must verify, and prints a summary
  of the full desired set of labels and issues; `--out DIR` also writes every issue body and `plan.json`.
  No network.
- `apply` uses the GitHub REST API with `GITHUB_TOKEN` and `GITHUB_REPOSITORY`.
  - **Idempotent.** Each issue body carries a hidden marker, `<!-- ophanim:item=<id> -->`. The publisher
    finds its issues by that marker and updates them (only the fields that differ) instead of creating
    duplicates. A second run over an unchanged ledger writes nothing.
  - **Owns only what it marks.** An issue is the publisher's only if it carries the marker; a label only
    if its description starts with `ophanim:`. It never edits, closes or deletes anything else. A label of
    the same name owned by someone else is left as is. Labels outside its namespace that a person adds to
    one of its issues are kept.
  - **Rate-limit friendly.** Requests are sequential with a pause between writes; a rate-limit response
    is waited out (up to a minute) and any other non-2xx response stops the run with its status and body.
- **Projects v2** sync is opt-in: with `PROJECT_URL` (`https://github.com/users|orgs/<owner>/projects/<n>`,
  a repository variable `OPHANIM_PROJECT_URL` in the workflow) or `PROJECT_ID`, and the secret
  `OPHANIM_PROJECT_TOKEN` (a personal access token with `project` scope; `GITHUB_TOKEN` cannot write a
  user-owned project), each issue is added to the project and its Status set where an option matches the
  state. Without them the sync is skipped and the reason logged.

The workflow `.github/workflows/public-record.yml` runs only on push to `main` and by hand
(`workflow_dispatch`), never on pull requests, with `permissions: issues: write, contents: read`. It
verifies the status ledger, writes the plan to the run summary, then applies it.

## Pull request provenance

```sh
node ophanim/public/github.mjs pr-provenance --ledger <dir> [--cycle <hash> | --scope <name>] [--anchor <sha256:...>]
```

prints a "Provenance" section to paste into, or append to, a pull request body: the seats that produced
the work (from the author turns the cycle cites) and the seats that reviewed it (role, vendor, requested
and served model, lab, seat key id, entry hash, verdict), the independence evidence and its limits, every
finding with its resolution (fixed, with the test that failed before and passed after; deferred, with the
reason; unreproduced, marked), and the cycle's close outcome, or why it cannot close yet. The ledger is
opened read-only and verified in full against its pinned anchor first; no key is needed.

## Cycle reports

```sh
node ophanim/public/github.mjs cycles [--ledger <dir>] [--out docs/cycles]
```

writes `docs/cycles/<scope>-<n>.md` for every cycle (what was, what is, what could be better, what the
system concluded) and `docs/cycles/index.md`. The default ledger is the review-cycle CLI's own,
`<git common dir>/pantheon-cycles`. These files are generated; regenerate them, do not edit them.

## Tests

`ophanim/public/public-record.test.mjs`, run by `npm run test:proof` (no network: apply runs against an
in-memory fake of the REST API, the review cycle against scripted reviewers). The `owner_role` field is
tested in `packages/ledger/tests/status.test.mjs`.
