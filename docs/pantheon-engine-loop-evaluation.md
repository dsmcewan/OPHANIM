# Loop evaluation: the Pantheon engine and its 1 + 4 arrangement

This extends [loop-evaluation.md](loop-evaluation.md) (OPHANIM's controller, P1–P9) and [pantheon-model-loop-evaluation.md](pantheon-model-loop-evaluation.md) (per-model call paths, M1–M3). The same loop applies, with no new architecture. Pantheon and its modes are subjects of stabilize → identify → propose → apply → validate → record delta → hand off on match → converge.

Scope:
- `pantheon/src/index.mjs` and the engine it exports: `board/*` (CAS, refs, DAG, controller, `ship`) and `runOpenItem`.
- The chair layer: `team/roster`, `team/modes`, `team/law`.
- Seating: `role/seating`, `route/*`.

## 1. The 1 + 4 arrangement as Pantheon defines it

`team/roster.mjs` fixes five chairs. One coordinates, and four are modes.

| Chair | Role(s) | Pod / projection | Standing? | May |
|---|---|---|---|---|
| `lead@orch` (**coordinating**) | planner | orch / planner | standing | open modes; never writes the tree, ships or judges |
| `impl@build` | implementer | build / worker | standing | write the tree under a named lease; cannot mark its own work done |
| `check@review` | reviewer | review / checker | standing | pass or fail the gate; cannot merge |
| `scout@opt` | scout, explorer, advocate | opt / isolated_debater | on request, turn cap 3 | answer a bounded question in an isolated fork |
| `arbiter@judge` | judge | judge / synthesizer | on request, turn cap 2 | name the disagreement between forks it did not produce |

Two facts frame everything below:
- **The coordinating model does not schedule.** Scheduling is deterministic code: `controller.schedule()` over board predicates.
- **No chair ships.** Integration is `ship()`, run by the controller (law 6, the ACTOR gate).

So "1 + 4" is five *occupied chairs*. The loop runner is not a model.

## 2. Pantheon mechanisms mapped to loop steps

| Loop step | Pantheon mechanism | Where | Matches? |
|---|---|---|---|
| **Stabilize on the known** | The board head `refs/board/<ref>` is a merkle-DAG commit. `boardState` reads only committed slots. Seat conversations carry a hash chain, checked before reuse (M3). Resume re-checks each saved artifact branch against its recorded bytes. | `controller.boardState`, `refs.resolve`, `run-item` resume branch | yes |
| **Identify the unresolved** | `boardStatus` is a deterministic ladder (intake, planning, executing, reviewing, stuck, split, awaiting_human, accepted). `schedule()` evaluates the trigger table (plan, work, critique, integrate, explore, refute, synthesize, discuss) and returns every candidate with why it was kept or dropped. Obligations are the ticket's `acceptance` rows plus the `item:*` work items. | `controller.boardStatus`, `schedule`, `TRIGGERS` | yes |
| **Research / propose against the known** | `lead@orch` writes the plan on its own wip ref. The work items are generated by code from the ticket's slots, not by the model. Implementers propose artifacts on fenced seat refs. Scouts propose evidence on isolated refs. | `run-item` plan and work stages | yes |
| **Assignment** (step 3 applied to coordination) | Which *pattern* runs is a function of board status (`modes.RENTED`): planning→delegate, executing→conveyor, reviewing→maker_checker, stuck→timeboxed_swarm, split→isolated_debate. Which *model* fills a chair comes from `SEATING` and `candidatesFor`, then `routeCall` (cooldown, pools). The reviewer is chosen to cut across the maker's and planner's labs (`assertReviewCutsAcross`). | `team/modes`, `role/seating`, `route/*` | partly (gaps E1, E2, E5) |
| **Apply** | A seat publishes under a named lease generation, and a fenced generation is refused at the ref swap. Revisions are bounded (`revisions`, default 3). The verdict is re-asked once, then fails closed. | `refs.swap`, `runtime.verify`, `run-item` work and review stages | yes |
| **Validate ground truth** | Acceptance is *executed*, never asserted. The command runs in a mandatory bwrap sandbox, and a repro counts only if it **cites the artifact's cid** and was run by the controller or another lab. Critiques bind to the exact bytes. `ship()` gates: ACTOR, TARGET, TICKET, GRAFT, LEASE, REVIEW (a cross-lab ack on these bytes), TESTS (green on these bytes), MERGE. Every model turn now needs the provider's successful terminal state (M1). | `acceptance.mjs`, `controller.acceptanceStatus`, `integrate.ship` | yes |
| **Record what changed** | The CAS is content-addressed, and a commit's tree is a map from slot to cid. A transition writes only the new entries; unchanged slots are carried by cid. That is the was/is pair, by construction. Runtime chrome (leases, occupancy, spend) is kept out of the hash on purpose so it cannot fork identities. | `cas`, `dag.publish`, `runtime.mjs` (L7) | yes, with gap E6 |
| **Handoff** | `refs.swap` is compare-and-swap on the expected head, under the same lock as the lease fence. Bound-review keeps artifacts off the shipping ref until `ship()`. Each gate re-derives from the two trees rather than from another gate's output. | `refs.swap`, `policy.shipOnlySlots`, `integrate.ship` | yes |
| **Converge or continue** | `accepted` means every item is done and acceptance is executed and passing. A refused ship is a no-op: nothing moves. | `boardStatus`, `ship` | yes; the run path does not loop on `schedule()` (E2) |

The matches are strong. Pantheon's DAG is already a delta-only, hash-linked trail. Its gates read the objects, not caller-supplied flags. And it keeps verification independent of the producer.

## 3. Gaps relative to the principle

Each gap was checked against the code at this commit.

**E1. The 1 + 4 chair layer is declared but not on the execution path.**
- `team/modes` (`patternFor`, `assertOpened`, `occupiedChairs`), `team/roster` (`occupy`, `nextOccupant`) and `team/law` (`enforce`) have no callers outside `src/team/` and the tests.
- `runOpenItem` seats models by role through `SEATING` and `candidatesFor`. It never checks that the stage it is running is the pattern `patternFor(boardStatus)` selects. It never checks that an on-request chair (scout) was opened by `lead@orch` within its turn cap.
- So the four modes' contracts are tested as tables but do not gate the runs that produce evidence. That is verification treated as optional, by omission.

**E2. The run path is a fixed script, not a loop over the controller.**
- `runOpenItem` runs intake → plan → work → acceptance → review → ship in order.
- It calls `schedule()` once, after planning, to check that work was scheduled. Later stages do not require the controller's predicate to agree before they run.
- The gates in `ship()` still catch a bad outcome at the end. But a stage can start from a state the controller would not have scheduled. That is a control path that is not itself the loop.

**E3. The model that produced an entry is not in the trail.**
- Board entry authors carry `vendor`, `seat_id`, `mode` and `occupancy_gen`, but no model.
- Fallbacks inside a vendor's ladder (for example sol → luna) and agy-lane models are recorded only in `run.json` and the progress stream. `run.json` is rewritten in place and is outside the hash-linked record.
- So the assignment of a model to a contribution cannot be checked against the trail.

**E4. Reseating is not a recorded transition.**
- Every seat is created with `occupancy_gen: 1`. A reviewer that falls through to another vendor gets a new `seat_id`, but the generation never advances.
- `roster.occupy` computes `gen` and `reseated`, but nothing calls it.

**E5. Assignment can choose a model outside the registry.**
- `SEATING` puts `claude-sonnet-4-6` and `claude-opus-4-6-thinking` on the agy CLI lane, at the top of both the planner and implementer ladders. Neither is in `models.json`.
- The agy CLI does check its own `SUCCESS` status. But the per-model walk (M1) and any registry-based evaluation cannot see these two seats, which are the default occupants.

**E6. Load-bearing state outside the trail.**
- `runtime.budget()` decides scheduling: when the budget is exhausted, every trigger except integrate is blocked. Its input is `spend.jsonl`, an append-only side log whose rows name a commit cid that is never checked to exist.
- `occupancy.json` is overwritten in place and lease history is capped at 50. Those are declared non-load-bearing, which is acceptable.
- `run.json` is the resume record. Resume re-checks artifact bytes against it, but not the record itself against the board.

**E7. Modes are adjusted by preference, not by the loop.**
- Every seating `basis` is TASTE, QUOTA, SURFACE or UNMEASURED; `router.UNMEASURED` says so honestly.
- Nothing derives each chair's contribution from the board, such as revisions to green, critiques later contradicted by executed acceptance, reseats or turns.
- So adjusting the 4 + 1 arrangement is an edit to a table, not a was/is transition with evidence. OPHANIM has that loop (its contribution registry, investigation ranking and signed scheduler decision), but Pantheon's chairs are not its subjects.

## 4. Proposals

Each proposal is a small was/is change whose acceptance the existing gates or tests can check. None adds a component.

**Q1. Put the occupant model in the author record (fixes E3).**
- Add an optional `model` string to the entry author schema (`board/schema.mjs` allowlist). `run-item` passes the routed `seat.model` when it publishes plan, work, critique and scout entries.
- *Was/is:* new entries carry it, and old entries stay valid.
- *Check:* the board-schema tests, plus one run-item test asserting that each artifact's and critique's author model equals the routed seat. Ship's REVIEW gate keeps judging labs by vendor.
- **Implemented.**
  - `schema.validateEntry` accepts an optional `author.model` (a model-id string) and still refuses any other author field. `dag.putCommit` keeps it on commit authors.
  - `run-item` publishes scout, plan, work and critique entries under the occupant that *answered*, not the one the table offered first.
  - Tests: `tests/board-occupancy.test.mjs` runs a whole scripted ticket and finds the model on every seat-authored entry (`openai/gpt-6-sol` built the slot, `anthropic/claude-fable-5-2` planned, `xai/grok-4.7` reviewed). Older entries without a model stay valid.

**Q2. Derive `occupancy_gen` from the board (fixes E4).**
- Compute it as 1 plus the number of distinct earlier occupants of the same seat mode on this board, read from the authors already in the DAG. Stop hard-coding 1.
- *Was/is:* a reseat is visible as an incremented generation on the entry itself.
- *Check:* a reseat test using the existing fallback fakes (`routeCall` with a 429 on the first pool).
- **Implemented, as a transition rather than a count.** `src/board/occupancy.mjs`:
  - `nextOccupancy` advances a chair's generation exactly when a different vendor or model answers it.
  - `occupancyTrail` re-derives every generation from the authors in order, and names the first one that does not follow.
- *Check:* `tests/board-occupancy.test.mjs` makes revision 1 fail acceptance and the pinned `gpt-6-sol` return 500 on revision 2. The chair falls through to `claude-opus-5-5`, and the trail shows `[rev 1, openai/gpt-6-sol, gen 1]` → `[rev 2, anthropic/claude-opus-5-5, gen 2]`, with one reseat. The test uses its own cooldown store: the default store is shared, and injected refusals would otherwise cool pools for concurrently running tests.

**Q3. Make the chair contracts gate the run (fixes E1), as checks only.**
- Before each stage, run three checks:
  - `patternFor(boardStatus(...))` must include the chair for that stage;
  - a scout stage needs `assertOpened({chair:'scout@opt', opened_by:'lead@orch', turns})`;
  - before `ship`, call `enforce(shipClaim(...))`, the bridge `integrate.mjs` already provides and nothing calls.
- A refusal is a recorded `run.error` at that stage and nothing moves. These are the existing declarations, put on the path that produces evidence.
- *Check:* existing `team-*` and `board-run-item` tests, plus one test where a stage is attempted from a board status whose pattern excludes its chair.
- **Implemented**, in `src/board/stage-gate.mjs`, and called from `runOpenItem`:
  - **plan** must run under `lead@orch`, with the `plan` trigger ready.
  - **work** must run under `impl@build`, with the `work` trigger ready for every slot's item, checked before any lease is taken.
  - **critique** must run under `check@review`, with the `critique` trigger ready for these exact offered bytes. Law 3 is then checked against the reviewer that actually answered.
  - **ship**: `assertLaw(shipClaim(...))`, so law 6 and law 7 run on facts the ship gates derive. A law check where no law applied is refused, not passed.
  - A refusal is a `StageRefused`, recorded as that stage's `run.error`, and nothing moves.
- **Corrected from the proposal:** the intake scouts are not `scout@opt`. They run before the board exists, with status `intake` and no pattern. They are the `INTAKE` fan-out, already bounded by `assertFanOutIsOutside`. `scout@opt` is the on-request explore chair the lead opens when the board is stuck, and `runOpenItem` never runs that mode. So the scout clause has no stage to apply to.
- **On resume**, the plan and work gates do not apply, because those stages are not re-entered from scheduling. The critique and ship gates apply on every run.

**Q4. Require the controller's predicate before each stage (fixes E2, without restructuring).**
- Generalise the one existing check (`sched.ready.some(r => r.ks === "work")`). Before critique and before integrate, require the matching trigger (`critique`, `integrate`) in `schedule().ready` for the item being handled.
- The stage order stays the same. A stage the controller would not schedule fails closed with the controller's own drop reason.
- *Check:* `board-run-item` tests. A deliberately unbound repro must make the integrate stage refuse before `ship()` is called.
- **Implemented.**
  - Before `ship()`, the controller must schedule `integrate` for every built item. Otherwise the run is refused through the same record a gate refusal uses: `shipped:false`, the dry-run ship `gates`, and a `ship_why` naming the unscheduled items, the controller's reason and the failing gates.
  - Integrate candidates that `schedule()` deferred only because another candidate already claims the shared `tree` resource still count as eligible, because `ship()` integrates every slot in one transaction.
- *Check:* `tests/board-stage-gate.test.mjs` covers four cases:
  - a planning board admits plan and refuses work and critique;
  - an executing board admits work only for its ready item, and refuses a second plan and a ship;
  - same-lab and assigner-lab reviews are refused by law 3, and an unknown action is never a pass;
  - a full run whose acceptance never passes is refused at integrate. Its `ship_why` names the item and the TESTS gate, the gates are still recorded, and nothing is exported as certified.
- **Results:** Pantheon's full suite gives 774 pass and the same 1 environment-only failure. OPHANIM is unchanged.

**Q5. Keep the seating table inside the registry (fixes E5).**
- Add a `transport` section to `models.json` listing agy-lane model ids (`claude-sonnet-4-6`, `claude-opus-4-6-thinking`) under their CLI lane. Add a config test: every model named in `SEATING` resolves either in the registry or in that section.
- The per-model walk (`model-terminal-state.test.mjs`) gains a case for the agy CLI lane's `SUCCESS` check.
- *Check:* `config-models.test.mjs`.
- **Implemented.**
  - The lane list went into a separate `src/config/lanes.json`, not into `models.json`. Several callers iterate `models.json` as `vendor → models`, and a new top-level key would read there as a fifth vendor.
  - `config/models.mjs` exports `LANES` and `resolveSeatModel`.
  - `config-models.test.mjs` resolves every model in `SEATING` and `INTAKE`. It asserts that the lane models are exactly the seated models outside the registry.
  - `tests/agy-cli-terminal.test.mjs` drives `runAgyCliTurn` with a fake `agy` executable for both lane models. `SUCCESS` is accepted; `ERROR`, `CANCELLED` and a missing status are refused.

**Q6. Bind budget spend to commits that exist (fixes E6's load-bearing part).**
- `runtime.budget()` counts a spend row only if its `commit` resolves in the store. Rows that don't resolve are reported (`unbound_rows`) rather than counted silently.
- *Check:* a runtime test with one bound row and one forged row.
- `run.json` can be bound later by writing its digest into a controller trace entry at each stage. That is noted here, not proposed now.
- **Implemented.**
  - `openBoard` passes its store to `openRuntime`. `budget()` counts a spend row only if its `commit:` cid is in that store, and reports `binding` and `unbound_rows`.
  - A runtime opened without a store reports `binding: "unchecked"` rather than claiming a check it did not make.
  - *Check:* `tests/board-budget-binding.test.mjs`. Three forged rows (an absent commit, a malformed one, and another absent one) add nothing, cannot exhaust the budget, and are reported. Real spend still exhausts it and blocks the spending triggers.

**Q7. Let the 1 + 4 arrangement be adjusted by OPHANIM's existing loop (fixes E7, once Q1 and Q2 exist).**
- *Derive, don't store:* a per-chair contribution projection from the board. For each chair it gives the occupant model (Q1), the generation (Q2), revisions to the first green acceptance, critiques whose verdict disagreed with the later executed acceptance, turns, and reseats.
- Feed it to `efficiency/contributions.mjs` as variables of a scope. Investigation then ranks which chair question is worth measuring, as it already does for scheduler latency.
- A seating change remains a signed, scoped decision, admitted exactly like the 1 → 3 slot policy. Until the TELOS-side verifier admits that dimension (it is pinned), Q7 produces ranked questions and evidence only, never a seating change.
- *Check:* `investigate --state` reproduces the receipt from the board.
- **Measurement implemented; adjustment is On Hold** because it needs the pinned verifier to admit seat changes.
  - `pantheon/src/board/contributions.mjs` derives each chair's projection from every entry reachable from the board's refs, and stores nothing. It covers:
    - occupants, with vendor and model (Q1);
    - reseats re-derived per chair instance by `occupancyTrail` (Q2), with inconsistent or pre-Q1 trails reported rather than counted as zero;
    - implementer revisions per slot and the first revision an independent run passed;
    - reviewer verdicts and approvals contradicted by executed acceptance;
    - plans and scout forks.
  - `verifyChairContributions` recomputes the projection and refuses one that does not match the board.
  - `ophanim/efficiency/investigation/chairs.mjs` turns the projection into functional models, one per chair, with `rework` and `reseats` as board-derived observations. It ranks the questions through the existing `selectInvestigation`. Without a declared forecast the outcome is `insufficient_evidence`; with one, the question is ranked by information value.
  - Every result keeps `executionAuthorized`, `promotionAuthorized`, `modelCalls`, `replays` and `effects` at false or zero.
  - *Check:* `pantheon/tests/board-contributions.test.mjs` runs a real refused-then-revised two-slot ticket. It derives 2 revisions per slot (green on revision 2), verdicts of 2 approve and 2 request_changes, no contradicted approvals, and no reseats. It verifies the projection by recomputing it, refuses a forged one, and feeds it to the ranking. `ophanim/efficiency/investigation/chairs.test.mjs` covers the ranking itself.

## 5. What does not change

- The controller stays code, and integration stays `ship()`.
- No chair gains authority.
- The DAG stays the record.

All seven proposals add checks or record facts that already exist at runtime, so the underlying system keeps operating throughout. The loop stays the only process: Pantheon's stages are steps of it, the 1 + 4 chairs are its workers, and choosing and adjusting them is the same loop applied to coordination.
